# 无钱包插件接入方案调研

本文调研浏览器没有钱包插件时可采用的身份来源、登录协议和授权方式。表中的候选路线不等于 `web3-bs` 已经实现或内置对应钱包连接能力。

当前系统已经落地的无插件钱包身份路线是 Wallet Identity authorization code + PKCE + Passkey；`web3-bs` 记录其接入契约，不提供对应的浏览器 SDK 方法。`web3-bs` 已为中心化会话和中心化 UCAN 提供客户端 API；WalletConnect、Deep Link、嵌入式钱包和传统账号系统需要 DApp 自行接入外部实现。

## 1. 快速对比

| 路径 | 身份来源 | web3-bs 当前状态 | 推荐场景 |
| --- | --- | --- | --- |
| Wallet Identity + Passkey | 钱包身份 DID | 已提供接入文档；流程由 DApp 后端调用 Node HTTP 接口 | 无插件登录已有钱包身份 |
| 钱包 App 连接（WalletConnect / Deep Link） | 链上钱包 | 可接收外部注入的 EIP-1193 Provider；不内置连接桥 | 需要保留链上地址控制权证明 |
| 嵌入式钱包（托管 / MPC） | 钱包 SDK | 可接收 SDK 提供的 EIP-1193 Provider；不内置钱包 SDK | 可接受第三方钱包 SDK 成本 |
| SSO / WebAuthn（JWT） | 中心化身份 | 提供应用 token 存储和请求工具；不实现认证服务 | 业务不需要钱包身份语义 |
| 中心化 UCAN 发行 | 中心化身份和 Issuer | 已提供中心化 UCAN 客户端 API | 接受中心化 Issuer 信任模型 |
| 首次钱包绑定 + 长期会话 | 钱包身份和 DApp 会话 | 提供钱包登录及 token 工具；绑定协议由 DApp 定义 | 允许首次使用钱包，后续免钱包 |
| 传统账号（手机号、邮箱、2FA） | 中心化账号 | 提供应用 token 工具；不实现账号系统 | 业务使用自己的中心化账号 |

## 2. 决策顺序

1. 是否需要登录已有 Wallet Identity DID？需要时使用 Passkey 无插件身份登录。
2. 是否必须证明链上地址控制权？需要时接入钱包 App 或嵌入式钱包提供的 Provider。
3. 是否接受独立于钱包身份的中心化账号？接受时选择 SSO、WebAuthn 或传统账号。
4. 是否需要 UCAN 资源授权？需要时再独立选择钱包 UCAN 或中心化 UCAN。

## 3. 路径详解

### 3.1 Wallet Identity + Passkey

这是当前已经落地的无插件钱包身份登录方式。用户使用绑定到 Wallet Identity DID 的通行证认证，DApp 后端通过 authorization code + PKCE S256 获得 DID 和已授权身份凭证。

该流程不经过 EIP-1193 Provider，不获取 `eth_accounts`，也不证明用户当前控制某个链上账户。完整契约见[无插件身份登录接入](../身份授权/无插件身份登录接入.md)，通行证生命周期见[通行证接入](../身份授权/通行证接入.md)。

### 3.2 钱包 App 连接（WalletConnect / Deep Link）

适用：

- 用户愿意安装钱包 App
- 业务希望保留链上身份
- 希望移动端体验接近 PC 钱包插件

核心前提：

- 移动端可拿到 EIP-1193 provider
- 若使用钱包托管 UCAN session，钱包需支持 `wallet_ucan_session` / `wallet_ucan_sign`

外部连接桥向页面提供 EIP-1193 Provider 后，可以使用的 `web3-bs` 组合：

- 登录：`requestAccounts` + `loginWithSiwe` + `authFetch`
- SIWE Root Proof + UCAN：`createUcanSession` + `getOrCreateUcanRoot({ proof: { type: 'siwe' } })` + `createInvocationUcan`
- WebDAV：`initWebDavStorage` 或 `createWebDavClient`

`web3-bs` 不创建 WalletConnect 会话，也不实现 Deep Link 路由。

### 3.3 嵌入式钱包（托管 / MPC）

适用：

- 不希望用户额外安装插件
- 可以接受钱包 SDK、合规和运维成本

核心前提：

- 嵌入式钱包 SDK 可暴露 EIP-1193 provider
- 若仅支持 `personal_sign`，则只适合 SIWE/JWT 路线

外部钱包 SDK 提供 EIP-1193 Provider 后，可以使用的 `web3-bs` 组合：

- 登录：`requestAccounts` + `loginWithSiwe` + `authFetch`
- UCAN（可选）：钱包实现 UCAN RPC 时使用钱包托管 session；否则由 DApp 明确创建本地 session
- WebDAV：`createWebDavClient` / `initWebDavStorage`

`web3-bs` 不内置嵌入式钱包或 MPC 实现。

### 3.4 SSO / WebAuthn（JWT）

适用：

- 登录成功率和移动端体验优先
- 不强依赖链上身份语义

核心思路：

- 认证后端完成 SSO 或 Passkey 验证并签发 JWT
- DApp 使用 JWT 调用多后端

认证服务签发 token 后，可以使用的 `web3-bs` 组合：

- `setAccessToken` + `authFetch` + `refreshAccessToken`
- WebDAV 使用 `createWebDavClient`（Bearer JWT）

备注：

- 该路径不依赖钱包，不使用钱包 UCAN。

如果目标是登录已有钱包身份 DID，而不是建立独立的中心化账号，应使用 Wallet Identity authorization code + PKCE + Passkey。完整流程见[无插件身份登录接入](../身份授权/无插件身份登录接入.md)。

### 3.5 中心化 UCAN 发行

适用：

- 希望保持 UCAN 令牌形态
- 接受中心化 Issuer 信任模型

核心思路：

- 用户先走中心化登录（SSO/WebAuthn/JWT）
- Issuer 服务签发 UCAN（`iss` 为 Issuer DID）
- 业务后端信任 Issuer 公钥并校验 `aud` / `cap` / `exp`

`web3-bs` 推荐组合：

- `getCentralIssuerInfo`
- `createCentralSession`
- `issueCentralUcan` / `createAndIssueCentralUcan`
- `authCentralUcanFetch`

边界说明：

- 这是“中心化 UCAN”，不是“用户钱包控制 UCAN”。

### 3.6 首次钱包绑定 + 长期会话

适用：

- 用户可以完成一次钱包认证
- 后续浏览器希望免钱包访问

核心思路：

- 钱包登录后，DApp 后端签发一次性绑定票据
- 其他设备绑定后换取 DApp 长期会话

`web3-bs` 推荐组合：

- 钱包端：选择 SIWE 或 Wallet Identity 登录
- 无钱包端：`setAccessToken` + `authFetch` + `createWebDavClient`

该绑定票据、设备登记和长期会话协议由 DApp 后端定义，不是 web3-bs 内置协议。

### 3.7 传统账号（手机号、邮箱、2FA）

适用：

- 业务不依赖链上身份
- 优先追求实现效率和稳定性

核心思路：

- 账号体系签发 JWT
- 多后端统一校验 JWT

`web3-bs` 推荐组合：

- `setAccessToken` + `authFetch` + `refreshAccessToken`
- WebDAV：`createWebDavClient`

## 4. 调研结论

### 4.1 先定“身份来源”，再定“令牌形态”

- 身份来源：钱包 / SSO / 账号体系
- 令牌形态：JWT / 钱包 UCAN / 中心化 UCAN

这两个维度分开设计，文档和实现会更清晰。

### 4.2 优先使用统一资源模型

无论 JWT 还是 UCAN，资源权限建议统一到服务端策略，例如：

- `app:all:<appId>`
- `app:read:<appId>`
- `app:write:<appId>`

这样可减少多后端权限映射成本。

### 4.3 明确中心化 UCAN 的信任边界

- 钱包 UCAN：用户控制签名能力
- 中心化 UCAN：Issuer 服务控制签发能力

这两者在安全语义上不同，文档与产品上应明确标注。

本文不把所有无插件路线归并为一个登录协议。Wallet Identity、SIWE、中心化登录和 UCAN 保持独立；`web3-bs` 只在对应协议已经存在时提供调用工具。
